1. Problem Statement
Voice and audio communication requires considerably more data than text, making it difficult to transmit voice over low-data-rate or bandwidth-constrained links. However, in emergencies and distress situations, voice is more useful and inclusive than written messages because people can communicate without depending on literacy.
ISRO wants an Android application that can convert speech to text, transmit the text, and convert it back to speech — all locally on the device, using lightweight AI models with minimal latency.
2. Expected Solution
An Android-based multilingual voice transceiver where two phones exchange compact text instead of raw audio:
Phone A: Speech → On-device STT → Text
Text transmitted via Wi-Fi / Bluetooth
Phone B: Text → On-device TTS → Speech
Required languages (10):
Hindi, Gujarati, Marathi, Kannada, Malayalam
Tamil, Telugu, Odia, Bengali, English
3. Core App Functionality
A. Speech-to-Text
Listens locally, detects pauses/stoppages, identifies the completed sentence, converts speech to text, and transmits with minimal latency.
B. Text Transmission
Text is sent via Wi-Fi, Bluetooth, or a connected embedded device between two phones running the same app.
C. Text-to-Speech
The receiving phone converts the text back into speech and plays it through the speaker.
D. Walkie-Talkie Mode
Push-to-talk: hold to speak, release to send (STT → transmit → TTS). When push-to-talk is off, the app should behave like normal phone communication.
4. Core Idea
Traditional approach: Voice → Audio → Transmission → Audio
Proposed approach: Voice → Text → Low-bandwidth transmission → Text → Voice
5. Use Cases
Emergency & distress communication: 
Send critical messages even under extreme bandwidth limits.
Low-bandwidth communication: 
Text replaces continuous audio on constrained channels.
Space / remote communication: 
Directly relevant given ISRO's bandwidth and compute constraints.

Works where internet and cellular networks are unreliable.

Rescue and field teams exchange short voice messages reliably.
Phone-to-phone walkie-talkie: 
Direct Wi-Fi/Bluetooth communication — strongest demo scenario.

7. Proposed Innovation
Core idea: an offline, multilingual, lightweight AI transceiver that converts speech to compact text, transmits it over a low-bandwidth local link, and reconstructs intelligible speech on the receiving device.
Innovation 1 — Voice Without Transmitting Audio
Voice → Text → Transmission → Voice, reducing the information that needs to be sent.
Innovation 2 — Fully Offline AI
STT and TTS run entirely on-device, with no cloud API dependency — a hard requirement of the PS.
Innovation 3 — Lightweight AI for Low-End Devices
Optimize jointly for model size, RAM, CPU, battery, inference time, and accuracy using quantization, model compression, and efficient runtimes.
Innovation 4 — Pause-Based Sentence Detection
Wait for a natural pause before transmitting a full sentence, rather than sending partial fragments continuously.
Innovation 5 — AI Walkie-Talkie
Push → Speak → Release → Send → Receive → Hear — internally transmitting text, not audio.
Innovation 6 — Priority Emergency Channel
Emergency messages trigger immediate TTS announcement and alert mechanisms on the receiving device.
Innovation 7 — Performance-Aware Model Selection
Select models per language/device class based on accuracy, size, CPU, and latency — matching the PS's own evaluation metrics.

11. One-Line Summary
SIH26173 asks us to build an offline, multilingual Android walkie-talkie that does not transmit voice/audio directly. Instead, it converts speech into text, sends the compact text via Wi-Fi/Bluetooth, and converts the received text back into speech on another phone.

Bottom line: SIH26173 is technically strong and feasible, since the individual technologies (STT, TTS, mobile inference) already exist. The real differentiator is making the complete pipeline lightweight, offline, multilingual, accurate, and low-latency on low- and mid-range Android phones. The biggest risk is the 10-language requirement — the strongest strategy is to build an excellent end-to-end system first, then expand language coverage while continuously measuring WER, TTS intelligibility, model footprint, CPU/RAM usage, and end-to-end latency.
